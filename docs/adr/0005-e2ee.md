# ADR 0005: Ende-zu-Ende-Verschlüsselung mit Schlüssel im Link-Fragment

**Status:** angenommen (24.11.2026)

## Kontext
LiveKit entschlüsselt als SFU nur die Transportschicht (DTLS-SRTP). Wer den Server betreibt (oder übernimmt), könnte
Bild und Ton mitschneiden. Manche Runden wollen das ausschließen. livekit-client bringt E2EE mit (SFrame-ähnlich,
AES-GCM je Frame im Worker; Chrome/Edge/Firefox über Insertable Streams, Safari über `RTCRtpScriptTransform`).
Offen war, wie der gemeinsame Schlüssel zu den Teilnehmenden kommt, ohne dass der Server ihn sieht.

## Entscheidung
- **Optional je Raum**, vom Host im Konto (Planen/Bearbeiten) oder in der Lobby eingeschaltet.
- Der Host-Browser erzeugt ein **Geheimnis** (32 Zufallsbytes, base64url) und hängt es als Fragment an den Link:
  `/r/<code>#k=<geheimnis>`. Fragmente schickt der Browser nie an den Server. „Link kopieren“ (Konto, Meeting-Info,
  Mehr-Menü) enthält es; das Host-Gerät merkt es sich in `localStorage` je Raum.
- Daraus leitet jeder Browser per **HKDF-SHA-256** (Salz `agora-e2ee-v1`) zwei unabhängige Werte ab: den
  **Medienschlüssel** (`info "medien"`, 32 Byte → `ExternalE2EEKeyProvider.setKey`, AES-256-GCM) und einen
  **Prüfwert** (`info "pruefwert"`, 16 Byte). Nur der Prüfwert liegt beim Server. Die Lobby vergleicht ihn vor dem
  Beitritt und meldet einen falschen oder fehlenden Schlüssel sofort („Der Schlüssel passt nicht …“). Aus dem Prüfwert
  lässt sich bei 256 Bit Zufall weder Geheimnis noch Medienschlüssel berechnen.
- Im Meeting: Schloss-Pille „Ende-zu-Ende verschlüsselt“ (aus `room.isE2EEEnabled`), Banner bei
  `RoomEvent.EncryptionError` mit den betroffenen Namen.
- Datenkanal: Wir nutzen die Option `encryption` (nicht das veraltete `e2ee`) – damit sind auch Nachrichten zwischen
  Browsern verschlüsselt (Reaktionen, Hervorheben, Anmerkungen). In E2EE-Meetings nimmt der Client solche Nachrichten
  nur verschlüsselt an, damit der Medienserver keine fälschen kann.
- **An/aus und neuer Schlüssel** nur, solange niemand verbunden ist (sonst 409): Ein Meeting mit gemischten Schlüsseln
  hätte nur Fehlermeldungen.
- Der E2EE-Worker wird von Vite gebündelt (`livekit-client/e2ee-worker?worker`) und von `'self'` ausgeliefert –
  keine CSP-Änderung nötig.

## Grenzen (bewusst)
- **Chat, Umfragen, Host-Steuerung, Namen, Hand heben** laufen über den Server (ADR 0002) bzw. die Signalisierung und
  sind nicht Ende-zu-Ende-verschlüsselt. Der Server sieht weiter, wer wann teilnimmt.
- **Breakout-Räume** nutzen denselben Schlüssel (eigener Worker je LiveKit-Raum). Ein eigener Schlüssel je Breakout
  bräuchte eine Verteilung über den Server – das widerspräche dem Ziel.
- **Aufzeichnung:** Die Browser-Aufnahme (ADR 0003) funktioniert, wird aber in E2EE-Meetings **nicht hochgeladen**,
  sondern nur zum Herunterladen angeboten. Server-seitige Aufzeichnung/Streaming (LiveKit Egress) kann E2EE-Medien
  nicht entschlüsseln und ist für solche Räume nicht möglich – Egress-Funktionen sollen `raum.e2ee` prüfen und ablehnen.
- **Einladungs-Mails, Kalender-Links und `.ics`** enthalten den Schlüssel nicht (sonst läge er beim Mail-Server); der
  Host teilt den Link mit Schlüssel selbst. Der Einladen-Dialog weist darauf hin.
- Geht der Schlüssel verloren (anderes Gerät, Speicher gelöscht), kann ihn niemand wiederherstellen; der Host erzeugt
  einen neuen (alte Links gelten dann nicht mehr).
- Keine Verifikation der Teilnehmenden über den Schlüssel hinaus: Wer den Link hat, kann mithören. Schlüsselrotation
  beim Verlassen gibt es nicht.
- Browser ohne Encoded Transforms (sehr alte Versionen) können E2EE-Meetings nicht betreten (Hinweis in der Lobby).

## Folgen
+ Der Server (und wer ihn übernimmt) sieht von E2EE-Meetings weder Bild noch Ton noch Bildschirm
+ keine neue Schlüsselinfrastruktur, kein Konto nötig – der Link ist der Zugang
− etwas mehr CPU im Browser (Frame-Verschlüsselung im Worker), kein Server-Mitschnitt
− Schlüssel im Link: Wer den Link weiterleitet, gibt den Schlüssel weiter (Browser-Verlauf enthält ihn)
